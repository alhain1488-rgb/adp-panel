# CLAUDE.md

Этот файл Claude Code читает автоматически в начале каждой сессии. Здесь — только то,
что нельзя вывести из кода: правила работы, инварианты архитектуры и команды.
Полное ТЗ — в `docs/SPEC.md`, пошаговый план — в `docs/ROADMAP.md`.

## Что мы строим

Веб-панель управления несколькими VPS с Xray для **личного использования**. Одна панель
на главном VPS централизованно управляет прокси на всех серверах по SSH: серверы, inbound-ы
разных протоколов, клиенты и их подписки. Никакого биллинга, оплат, лимитов трафика,
рефералок — этого в проекте нет и быть не должно.

Протоколы MVP: **VLESS (Reality и TLS), VMess, Trojan, Shadowsocks** — нативно через xray-core;
и **Hysteria2 — обязателен** — через отдельный движок на ноде (`sing-box` или бинарник `hysteria`),
т.к. Hysteria2 (QUIC) в xray-core как inbound не существует. Детали — в `docs/SPEC.md §5`.

Стек: **Go** (backend) · **React + TypeScript** (frontend) · **SQLite** · **Docker Compose**.

## Порядок верхнего уровня (жёсткий, задаёт всю работу)

1. **Мок-фронт** — сначала полный frontend на моках (без backend), чтобы человек посмотрел и
   поправил UI/UX. → **СТОП, ревью человеком.**
2. **Backend + интеграция** — только после одобрения фронта: полноценный Go-backend, фронт
   переключается с моков на реальный API, всё поднимается **локально**.
3. **Деплой на VPS** — по SSH разворачиваем панель на VPS человека (IP и login/pass Claude Code
   запрашивает у человека в этот момент). → **СТОП, человек проверяет, что панель работает на его VPS.**
4. **Git** — только после того, как человек увидел рабочую панель на своём VPS, делаем `git push`.

Подробная разбивка на фазы — в `docs/ROADMAP.md`. Идём **строго по фазам, не забегая вперёд**.

## Как ты работаешь над этим проектом (правила, обязательны к соблюдению)

1. **Идём строго по `docs/ROADMAP.md`, фаза за фазой. Не забегай вперёд.** Внутри фазы
   можешь планировать свободно.
2. **Завершение фазы = ритуал:** прогнать команды проверки из фазы → убедиться, что всё
   зелёное (тесты, `go vet`, линтер) → `git commit` **локально** по Conventional Commits →
   дописать короткую запись в `docs/PROGRESS.md` (что сделано, что проверено) → следующая фаза.
   **`git push` НЕ делаем до финальной фазы** — до тех пор, пока человек не увидит панель
   запущенной на своём VPS. Локальные коммиты — это чекпоинты (можно откатиться), в удалённый
   репозиторий ничего не уходит раньше времени.
3. **Реальный VPS трогаем только в фазе деплоя, и только с данными от человека.** При разработке
   вся работа с серверами идёт через **моки** (интерфейсы) и **локальные dockerized-ноды** в `test/`
   (Xray-нода и Hysteria2-нода). Реальный VPS человека Claude Code разворачивает **только** в
   выделенной фазе деплоя (после одобрения фронта), запросив у человека **IP и SSH login/pass в
   этот момент**. Эти данные используются только в рамках сессии, **никогда не хардкодятся и не
   коммитятся** в репозиторий.
4. **Не выдумывай секреты.** Ключи, пароли, домен, SSH-доступ читаются из окружения либо
   запрашиваются у человека (данные деплоя). Если обязательная переменная не задана — падай с
   понятной ошибкой. Ничего не хардкодь.
5. **Backend и frontend строго разделены.** Общаются только через REST API и сгенерированные
   типы. Никакой общей кодовой базы. Мок-фронт реализует тот же контракт (`docs/openapi.yaml`),
   что и реальный backend, — чтобы переключение с моков на API было минимальным.
6. **Новый протокол добавляется ТОЛЬКО через реестр протоколов** (`internal/protocols`).
   Схема БД при добавлении протокола **не меняется** — протокол-специфичные параметры живут
   в JSON-полях. Это касается и Hysteria2: его параметры хранятся в тех же JSON-полях, отличается
   только целевой движок на ноде (см. инварианты). Если для нового протокола хочется новую
   колонку — это ошибка дизайна, стоп.
7. **Тесты пишутся вместе с кодом.** Фаза не закрыта, пока её тесты и линтер не проходят.
8. **Миграции аддитивные и применяются автоматически при старте.** Уже применённую миграцию
   не редактируем — добавляем новую.
9. **Если реально заблокирован** (нужен настоящий секрет/доступ, которого пока нет, или решение
   не покрыто спецификацией) — не угадывай. Запиши вопрос в `docs/QUESTIONS.md`, сделай что
   можешь без этого, и остановись на этом пункте.
10. **Язык:** код, комментарии и коммиты — на английском. Плановые документы (`docs/*.md`,
    этот файл) — на русском.

## Инварианты архитектуры (нарушать нельзя)

- **Модель доступа:** клиент получает доступ не к серверу целиком, а к конкретным inbound-ам.
  Связь `clients` ↔ `inbounds` — многие-ко-многим через `client_inbounds`.
- **Подписка собирается автоматически** из всех разрешённых и включённых inbound-ов клиента
  на всех серверах (включая Hysteria2-inbound-ы → `hysteria2://…` URI). Это единственный
  публичный (по токену) эндпоинт: `GET /sub/{token}`.
- **Секреты шифруются at-rest** (AES-256-GCM, мастер-ключ из `PANEL_ENCRYPTION_KEY`):
  SSH-ключи/пароли, TOTP-секрет. Пароль админа — только bcrypt-хэш.
- **Протоколы MVP:** VLESS (Reality и TLS), VMess, Trojan, Shadowsocks — через xray-core;
  **Hysteria2 (обязателен) — через отдельный движок на ноде** (`sing-box` или бинарник `hysteria`).
  Hysteria2 — это QUIC-протокол, **он не является inbound-ом xray-core** и не попадает в
  `config.json` Xray; для него генерируется отдельный конфиг своего движка. Обоснование и
  механизм — в `docs/SPEC.md §5`.
- **Sync-движок мультидвижковый.** На одной ноде могут работать и xray-core, и hysteria/sing-box
  одновременно. Sync раскладывает inbound-ы ноды по целевым движкам, генерирует конфиг **каждого**
  движка, валидирует каждый (`xray -test` для Xray; проверка конфига для hysteria/sing-box),
  делает бэкап и рестартит **каждый** соответствующий сервис. Идемпотентно по хэшу.
- **Деплой на реальный VPS** выполняется Claude Code **только** в фазе деплоя, с IP и SSH-данными,
  которые человек передаёт в этот момент. Раньше — никогда; в репозиторий эти данные не пишутся.

## Команды

Backend (из `backend/`):
```
go run ./cmd/panel        # запуск локально
go test ./...             # тесты
go vet ./...              # статический анализ
gofmt -l .                # проверка форматирования
golangci-lint run         # линтер (go install при отсутствии)
```

Frontend (из `frontend/`):
```
npm ci
npm run dev               # мок-фронт поднимается без backend
npm run build
npm run test
npm run lint
```

Локальные ноды для интеграции sync-движка (из `test/`):
```
docker compose -f test/xray-node/docker-compose.yml up        # Xray-нода
docker compose -f test/hysteria-node/docker-compose.yml up     # Hysteria2/sing-box-нода
# ассертим, что сгенерированные конфиги принимаются:  xray -test  /  проверка конфига hysteria|sing-box
```

Всё вместе локально (из корня):
```
docker compose up --build   # поднять панель целиком (backend + frontend + Caddy для HTTPS)
```

Деплой на VPS (фаза деплоя): Claude Code запрашивает у человека **IP, SSH login/pass** и
разворачивает панель на VPS по SSH. Данные — только в рамках сессии, не коммитятся.

## Definition of Done (весь проект)

По порядку верхнего уровня: **(1)** человек посмотрел и одобрил мок-фронт; **(2)** локально
`docker compose up` поднимает всю панель, фронт работает против реального API (вход с TOTP,
сервер, inbound-ы всех протоколов включая Hysteria2, клиент, рабочая subscription-ссылка + QR,
статистика на дашборде, Swagger на `/swagger`); **(3)** панель по SSH развёрнута на VPS человека
и человек убедился, что она там работает по HTTPS; **(4)** только после этого сделан `git push`.
README объясняет всё. Все тесты и линтеры зелёные.
