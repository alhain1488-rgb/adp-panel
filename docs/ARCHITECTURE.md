# ARCHITECTURE — ключевые решения и обоснования

Фиксирует архитектурные решения, которые нельзя вывести из кода. Дополняет `SPEC.md`
(что строим) и `ROADMAP.md` (в каком порядке). Решения по открытым вопросам —
в `QUESTIONS.md`.

---

## 1. Механизм управления нодами: SSH + файлы конфигов (не runtime-API)

Панель управляет каждой нодой по SSH: генерирует **полный** конфиг движка из его
inbound-ов и выданных клиентов, кладёт файл с бэкапом предыдущего, валидирует и
рестартит сервис.

**Почему так, а не gRPC/runtime-API Xray:**
- Надёжность и простота: конфиг на диске — единственный источник правды; после рестарта
  состояние воспроизводимо, «дрейфа» между runtime и файлом нет.
- Напрямую покрывает требования ТЗ: рестарт движка из UI, снятие CPU/RAM/диск по SSH.
- Один и тот же механизм работает для любого движка (Xray, sing-box/hysteria).

Горячее добавление пользователей без рестарта (gRPC HandlerService / API sing-box) —
осознанно отложено на будущее. В MVP: полная регенерация + рестарт, идемпотентно по хэшу.

## 2. Мультидвижковый sync

На одной ноде могут одновременно работать xray-core и Hysteria2-движок. Sync:

1. Берёт включённые inbound-ы ноды, группирует по `Engine()` из реестра протоколов.
2. Для каждого движка собирает конфиг: `config.json` (Xray) и/или конфиг sing-box/hysteria.
3. По SSH: бэкап текущего → запись нового → валидация (`xray -test`; проверка конфига
   Hysteria2-движка) → рестарт **соответствующего** сервиса.
4. Идемпотентность: сравнение хэша по каждому движку, пустые пуши пропускаются.
5. Пишет `last_sync_at` / `last_sync_error` на сервере.

Ошибка одного движка не должна ронять пуш другого — статусы независимы.

## 3. Реестр протоколов — единственная точка знания о протоколе

`internal/protocols`: интерфейс `Protocol` (`Name`, `Engine`, `BuildInbound`, `BuildLink`)
+ реестр `map[string]Protocol`. Добавить протокол = реализовать интерфейс и
зарегистрировать. **Схема БД при этом не меняется** — протокол-специфичные параметры
живут в JSON-полях inbound-а (`settings_json`, `stream_settings_json`, `sniffing_json`).

MVP-адаптеры:
- `Engine=xray`: VLESS Reality, VLESS TLS, VMess, Trojan, Shadowsocks.
- `Engine=hysteria`: Hysteria2.

Целевой движок inbound-а определяется его протоколом **через реестр**, а не отдельной
колонкой в БД.

## 4. Hysteria2 — почему отдельный движок

Hysteria2 — QUIC-протокол проекта Hysteria; его серверная часть **не реализована в
xray-core**, поэтому он не может быть inbound-ом в `config.json` Xray. На ноде для него
работает отдельный движок. **Решение (дефолт, см. QUESTIONS.md Q1):** `sing-box` —
единый JSON-формат, активная поддержка, задел под будущие протоколы. Hysteria2 задаётся
как inbound в JSON-конфиге sing-box.

- Аутентификация — по существующему полю `clients.password` (новых колонок нет).
- URI: `hysteria2://<password>@<host>:<port>/?sni=…&insecure=…#<remark>`.
- TLS обязателен. **Решение (дефолт, Q2):** самоподписанный серт на ноде + `insecure=1`
  на клиенте. Пути к сертам — node-side, задаются дефолтами движка или в `settings_json`.

## 5. Модель доступа: клиент → inbound-ы (многие-ко-многим)

Клиент получает доступ не к серверу целиком, а к конкретным inbound-ам, через junction
`client_inbounds` с уникальностью `(client_id, inbound_id)` и флагом `enabled` на уровне
выдачи. Подписка `GET /sub/{token}` собирается автоматически из всех разрешённых и
включённых inbound-ов клиента на всех серверах (включая `hysteria2://`). Это единственный
публичный (по токену) эндпоинт.

## 6. Шифрование секретов at-rest

AES-256-GCM, мастер-ключ из `PANEL_ENCRYPTION_KEY` (32 байта, base64). Шифруются:
SSH-ключ/пароль (`ssh_secret_enc`, `ssh_passphrase_enc`), TOTP-секрет (`totp_secret_enc`).
Пароль админа — только bcrypt-хэш (cost 12), не расшифровывается. Ключ читается из env;
при его отсутствии backend падает с понятной ошибкой (секреты не выдумываются).

## 7. Хранилище и слой доступа

SQLite (файл в volume). Слой доступа спроектирован под возможный переезд на Postgres:
без сырых SQLite-специфичных хаков в бизнес-логике. Миграции аддитивные, применяются
автоматически при старте; уже применённую миграцию не редактируем — добавляем новую.

## 8. Разделение backend/frontend

Общаются только через REST API и типы, выведенные из `docs/openapi.yaml`. Общей кодовой
базы нет. Мок-фронт (Фаза 1) реализует тот же контракт (`openapi.yaml`) через мок-слой
(MSW), что и реальный backend, — переключение с моков на API минимально (Фаза 7).

## 9. Стек и библиотеки (по SPEC §3)

- Backend: Go, роутер `chi`, `sqlc` + `golang-migrate`, `golang.org/x/crypto/ssh`,
  `pquerna/otp`, `google/uuid`, `skip2/go-qrcode`, `bcrypt`, stdlib `crypto/aes`+GCM,
  Swagger через `swaggo/swag` в синхроне с design-first `openapi.yaml`.
- Frontend: Vite + React + TS, React Router, TanStack Query, Tailwind + shadcn/ui,
  тема dark/light через CSS-переменные, мок-слой MSW.
- Деплой: Docker Compose (`backend`, `frontend`/static, `caddy` для TLS+reverse proxy).

Отклонения от дефолтов SPEC §3, если появятся, фиксируются здесь и в `PROGRESS.md`.
