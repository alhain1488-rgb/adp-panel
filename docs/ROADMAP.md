# ROADMAP — план автономной реализации

Это исполняемый план для Claude Code. Идём **строго по фазам**. Внутри фазы — свобода.
Ритуал завершения каждой фазы (обязателен): прогнать проверки → всё зелёное → `git commit`
**локально** (Conventional Commits) → запись в `docs/PROGRESS.md` → следующая фаза.

**Порядок верхнего уровня (задан человеком):** сначала мок-фронт для ревью → потом backend и
локальный запуск → потом деплой на VPS → и только после того, как человек увидел рабочую панель
на своём VPS, — `git push`. Поэтому:

- Работаем в ветке `build/mvp` (не в `main`).
- **`git push` не делаем до Фазы 9.** Локальные коммиты по ходу — да (чекпоинты), в удалённый
  репозиторий ничего не уходит, пока человек не подтвердит работу на VPS.

Есть **три точки ревью человеком**: после Фазы 1 (мок-фронт), после Фазы 8 (панель на VPS),
и Фаза 9 (git) выполняется только с явного разрешения.

Условные обозначения: **Цель** — что делаем; **Готово, когда** — критерии приёмки, проверяемые
командой.

---

## Фаза 0 — Контракт и каркас фронта

**Цель.** Зафиксировать API-контракт и типы, поднять каркас, чтобы мок-фронт строился на той же
поверхности, что и будущий реальный backend.

- `docs/ARCHITECTURE.md` — ключевые решения и обоснования (SSH-конфиг-механизм; мультидвижковый
  sync: Xray + Hysteria2/sing-box; реестр протоколов; модель доступа через inbound-ы; шифрование
  секретов; выбор движка для Hysteria2 — записать как решение, см. `SPEC.md §5` и `QUESTIONS.md`).
- `docs/ERD.md` — ER-диаграмма (mermaid) из `SPEC.md §4`.
- `docs/openapi.yaml` — **полный контракт API** (все эндпоинты из `SPEC.md §10`).
- Скелет каталогов из `SPEC.md §11`, `frontend/` scaffold (Vite + React + TS + Tailwind + shadcn),
  типизированный API-клиент, выведенный из `openapi.yaml`, и **мок-слой** (фикстуры/handlers,
  напр. MSW), реализующий контракт. `.gitignore`, пустые `docs/PROGRESS.md` и `docs/QUESTIONS.md`.

**Готово, когда:** `docs/openapi.yaml` валиден (линтер OpenAPI); `npm run build` проходит на
скелете; мок-слой отвечает по контракту; коммит Фазы 0 сделан локально.

## Фаза 1 — Мок-фронт (полный UI на моках)  ⟵ точка ревью человеком

**Цель.** Полный, «живой» frontend на мок-данных, без backend, — чтобы человек посмотрел и поправил
UI/UX **до** написания бэкенда.

- Все страницы, подключённые к мок-слою: **Login** (+ шаг TOTP), **Dashboard** (карточки серверов,
  метрики CPU/RAM/диск, счётчики, время синхронизации), **Servers/ServerDetail** (inbound-ы, в т.ч.
  выбор протокола включая Hysteria2; кнопки «проверить»/«рестарт»), **Clients/ClientDetail**
  (чекбоксы inbound-ов, ссылка, QR, скачать, обновить), **Settings** (домен/тема/2FA), **Logs**.
- Тёмная/светлая тема (CSS-переменные, переключатель сохраняется). Современный минимализм.
- Реалистичные мок-данные для всех сценариев (несколько серверов/протоколов/клиентов, ошибки, пустые
  состояния).

**Готово, когда:** `npm run build` и `npm run test` зелёные; `npm run dev` поднимает приложение
**без backend**; все страницы работают на моках; переключение темы работает.

> **СТОП.** Человек смотрит фронт и правит UI/UX. Дальше — только после его одобрения.

## Фаза 2 — Фундамент backend

**Цель.** Конфиг, БД с автомиграциями, шифрование, логирование, health.

- `config` — чтение и валидация env (`PANEL_ENCRYPTION_KEY`, `PANEL_ADMIN_USERNAME`,
  `PANEL_ADMIN_PASSWORD`, `PANEL_DOMAIN`, `PANEL_JWT_SECRET`, `DB_PATH`, …). Отсутствие
  обязательного — понятная ошибка на старте.
- `db` + `migrations` — схема из `SPEC.md §4`, миграции применяются автоматически при старте.
- `crypto` — AES-256-GCM (encrypt/decrypt) и bcrypt-обёртки.
- `logging` — структурный логгер. `httpapi` — сервер, `/healthz`, `/readyz`.

**Готово, когда:** `go test ./...` зелёный (миграции на чистой БД; AES round-trip; bcrypt verify);
`docker compose up` поднимает backend, БД мигрирует, `curl /healthz` → 200.

---

## Фаза 3 — Аутентификация и аудит

**Цель.** Вход админа, 2FA, журнал действий.

- Логин по bcrypt; сессия (JWT+refresh или cookie); middleware авторизации.
- TOTP: setup (otpauth-URL + QR), enable, verify. Секрет хранится зашифрованным.
- `audit` — middleware/хелпер, пишет все админ-действия в `audit_logs`.
- Первичный админ создаётся из env при первом старте. Rate-limit на логин.

**Готово, когда:** тесты на логин (успех/провал), полный цикл TOTP (setup→enable→verify),
запись в аудит; вручную через Swagger можно войти и включить 2FA.

---

## Фаза 4 — Управление серверами

**Цель.** CRUD серверов, SSH, метрики, статус и рестарт движков.

- CRUD `servers`; SSH-секрет шифруется при сохранении.
- `ssh` — клиент за интерфейсом (`Runner`): подключение по ключу/паролю, exec.
- Проверка доступности; IP + геолокация; определение статуса движков (Xray и, если есть,
  hysteria/sing-box); снятие CPU/RAM/диск.
- `POST /check`, `/restart-xray` (шире — рестарт нужного движка), `/stats`.

**Готово, когда:** юнит-тесты с мок-`Runner` (парсинг метрик, статуса, обработка ошибок SSH);
CRUD покрыт тестами; через Swagger (против мока) можно добавить сервер, увидеть статус, дернуть рестарт.

---

## Фаза 5 — Inbound-ы и реестр протоколов (включая Hysteria2)

**Цель.** Inbound-ы разных типов и сборка их в конфиг нужного движка.

- CRUD `inbounds` (в рамках сервера); протокол-параметры в JSON; генерация ключей Reality на бэкенде.
- `protocols` — реестр + адаптеры. Каждый адаптер знает свой **целевой движок**, умеет
  `BuildInbound` (фрагмент конфига для своего движка) и `BuildLink` (URI):
  - **xray-core:** VLESS Reality, VLESS TLS, VMess, Trojan, Shadowsocks.
  - **hysteria/sing-box:** **Hysteria2** (обязателен) → `hysteria2://…` URI; фрагмент конфига
    для движка Hysteria2 на ноде. См. механизм в `SPEC.md §5`.
- Валидация: для ≥3 xray-протоколов собранный inbound проходит `xray -test` на локальной ноде;
  собранный Hysteria2-конфиг проходит проверку конфига своего движка на локальной Hysteria2-ноде.

**Готово, когда:** тесты реестра (каждый адаптер строит валидный фрагмент и корректный URI, знает
свой движок); интеграция против `test/xray-node`: конфиг с VLESS Reality + VMess + Trojan
принимается `xray -test`; интеграция против `test/hysteria-node`: сгенерированный Hysteria2-конфиг
принимается его движком.

---

## Фаза 6 — Клиенты, доступы, подписка и мультидвижковый sync

**Цель.** Клиенты, выдача доступа к inbound-ам, подписка, sync по всем движкам ноды.

- CRUD `clients`; генерация UUID/password/токена; enable/disable.
- Выдача/отзыв доступа: `PUT /clients/{id}/inbounds` (связь `client_inbounds`).
- `subscription` — `GET /sub/{token}`: сборка base64-подписки из всех разрешённых/включённых
  inbound-ов клиента на всех серверах (xray-URI + `hysteria2://…`); QR; скачивание конфига; `rotate-token`.
- `sync` — **мультидвижковый** движок: для ноды собрать конфиг **каждого** движка (Xray `config.json`
  и, если есть Hysteria2-inbound-ы, конфиг hysteria/sing-box) → бэкап → запись → валидация каждого
  (`xray -test` / проверка hysteria) → рестарт каждого сервиса; идемпотентность по хэшу; запись
  `last_sync_*`.

**Готово, когда:** e2e-тест: создать клиента → выдать inbound-ы разных движков на разных серверах →
`/sub/{token}` возвращает валидную непустую подписку со всеми URI (включая `hysteria2://`); отзыв/disable
убирают их из подписки; sync против `test/xray-node` и `test/hysteria-node` пушит и проходит валидацию.

## Фаза 7 — Локальная сборка целиком (фронт на реальном API)

**Цель.** Один `docker compose up` локально, фронт переключён с моков на реальный backend, Swagger, README.

- Фронт: заменить мок-слой на реальный API-клиент (контракт тот же — `openapi.yaml`). Типы синхронны.
- Полный `docs/openapi.yaml` в синхроне с кодом; Swagger на `/swagger`.
- Caddy: TLS + reverse proxy на backend и статику фронта (локально — самоподписанный/staging).
- `README.md`: назначение, требования, локальный старт, переменные окружения, как добавить протокол
  (через реестр), как работает Hysteria2-движок, troubleshooting.
- Smoke-скрипт из `SPEC.md §12`.

**Готово, когда:** `npm run build`/`npm run test` и `go test ./...` зелёные; **локально**
`docker compose up` → панель по HTTPS → вход с TOTP → сервер (мок) → inbound-ы всех протоколов
(включая Hysteria2) → клиент → рабочая subscription-ссылка + QR → статистика на дашборде; Swagger доступен.

## Фаза 8 — Деплой на VPS по SSH  ⟵ точка ревью человеком

**Цель.** Развернуть панель на реальном VPS человека.

- Claude Code **запрашивает у человека:** IP/хост VPS, SSH-логин, SSH-пароль (и/или ключ), домен.
  Эти данные используются только в текущей сессии, **не пишутся в репозиторий и не коммитятся**.
- По SSH: доставить проект/образы на VPS, поднять `docker compose up` на VPS, Caddy выпускает TLS
  по `PANEL_DOMAIN` (домен должен вести на VPS — это делает человек).
- Проверить, что панель отвечает по HTTPS на VPS и вход работает. Перед необратимыми действиями —
  подтвердить целевой хост.

**Готово, когда:** панель развёрнута на VPS человека и человек **подтвердил**, что она работает по
HTTPS (вход, дашборд). Логи/результат деплоя — в `docs/PROGRESS.md` (без секретов).

> **СТОП.** Человек проверяет панель на своём VPS. Только после этого — Фаза 9.

---

## Фаза 9 — Git (push)

**Цель.** Только теперь выгрузить проект в удалённый репозиторий.

- Привести историю коммитов в порядок (логичные коммиты по Conventional Commits, ветка `build/mvp`).
- `git push` в удалённый репозиторий (с явного разрешения человека).

**Готово, когда (= Definition of Done проекта):** пройдены все три ревью (мок-фронт → локальная
работа → панель на VPS); проект выгружен в git; все тесты и линтеры зелёные; README полный.

## Что требует человека (Claude Code сам это НЕ делает)

1. **Заполнение `.env`** реальными секретами (мастер-ключ шифрования, JWT-секрет, логин/пароль
   админа, домен). Claude Code готовит `.env.example` и падает с понятной ошибкой, если чего-то нет.
2. **Данные для деплоя** (IP VPS, SSH login/pass, домен) — человек передаёт их Claude Code в Фазе 8
   по запросу. Claude Code не хранит и не коммитит их.
3. **DNS/домен** должен вести на VPS (Caddy сделает авто-выпуск TLS, но A-запись настраивает человек).
4. **Выбор движка для Hysteria2** (`sing-box` vs бинарник `hysteria`) и **стратегия TLS для Hysteria2**
   (самоподписанный + `insecure` на клиенте / реальный серт / ACME на ноде) — зафиксировать в
   `docs/QUESTIONS.md` и согласовать. Дефолт предложен в `SPEC.md §5`.
5. **Разрешение на `git push`** (Фаза 9) и финальное ревью — за человеком.
