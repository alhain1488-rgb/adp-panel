# QUESTIONS — блокеры и решения к согласованию с человеком

Здесь копятся вопросы, которые нельзя решить угадыванием. Для каждого указан
предложенный дефолт, чтобы работа не блокировалась там, где дефолт безопасен.

Формат: **статус** — `OPEN` (ждёт человека) / `DEFAULTED` (идём по дефолту, можно
переопределить позже) / `RESOLVED` (человек подтвердил).

---

## Q1 — Движок Hysteria2: `sing-box` vs бинарник `hysteria`
**Статус:** `DEFAULTED` → `sing-box`.
**Почему дефолт:** единый JSON-формат конфигов, активная поддержка, один движок под
будущие протоколы (SPEC §5). Реестр протоколов абстрагирует движок, так что смена
позже не трогает схему БД. Не блокирует Фазы 0–1 (мок-фронт движок не запускает).
**Нужно от человека:** подтвердить `sing-box` либо выбрать `hysteria`.

## Q2 — Стратегия TLS (панель и ноды) — «как в 3x-ui»
**Статус:** `RESOLVED` (2026-07-01) → **самоподписанные серты по умолчанию, реальные — если есть домен.**
Ровно как в 3x-ui: без домена — self-signed (панель под HTTPS с предупреждением браузера,
Hysteria2 с `insecure=1` на клиенте); с доменом — реальный серт через ACME/Let's Encrypt.
Никакой регистрации IP через сторонний сервис — «нет домена = self-signed».

**Механизм у нас:**
1. **Ноды:** при провижининге (§5.1) на ноде генерируется самоподписанный TLS-серт
   (`openssl`, CN/SAN = host/IP ноды). Панель запоминает пути к серту/ключу и подставляет их
   **по умолчанию** в новый Hysteria2- (и TLS-) inbound — аналог «Set cert from panel» в 3x-ui.
   Клиентский URI Hysteria2 при self-signed несёт `insecure=1`.
2. **Панель:** HTTPS обеспечивает Caddy. `PANEL_DOMAIN` = реальный домен с DNS на VPS →
   Caddy авто-выпускает Let's Encrypt. Иначе (только IP/localhost) → `tls internal`
   (самоподписанный CA Caddy), домен вводить не нужно.

**Нужно от человека:** подтвердить (это дефолт). Если есть домен — указать его в `PANEL_DOMAIN`,
тогда панель и (опционально) ноды получат доверенные серты.

## Q3 — Установка движков на ноды
**Статус:** `RESOLVED` (2026-07-01) → **панель сама устанавливает движки при добавлении
сервера** (xray-core + sing-box для Hysteria2). Изменение объёма относительно первоначального
ТЗ (раньше считали движки предустановленными).
**Решение человека:**
- Установка запускается **всегда автоматически** сразу после создания сервера (не по кнопке).
  Кнопка «Переустановить движки» остаётся для повторного запуска/восстановления.
- Поддерживаемые ОС нод: **только Debian/Ubuntu** (apt + systemd). Другие дистрибутивы —
  вне MVP; при их обнаружении провижининг падает с понятной ошибкой.
- Для Hysteria2 при установке генерируется самоподписанный TLS-серт на ноде (см. Q2).
**Требования к ноде:** root-SSH (или sudo) и исходящий доступ в интернет (GitHub/apt).
**Инвариант не нарушается:** это аддитивный модуль провижининга (`internal/provision`),
отдельный от sync-механизма; схема протоколов и реестр не меняются. Тестируется против
локальных dockerized-нод (базовый образ Debian без движков) в Фазах 5–6.

## Q4 — Docker в среде разработки
**Статус:** `RESOLVED` (2026-07-01) → установлен **Colima** + docker CLI + docker-compose
через Homebrew (`brew install colima docker docker-compose`, `colima start --cpu 4 --memory 4`).
Плагин compose слинкован в `~/.docker/cli-plugins/docker-compose`. Проверено: Фаза 2
поднимается через `docker compose up --build`, контейнер healthy, `/healthz` → 200.
**На заметку:** после перезагрузки Mac запустить демон — `colima start`.

## Q7 — Самостоятельная покупка подписки через бота
**Статус:** `RESOLVED` (2026-07-31).
**Проблема:** бот умел только привязывать созданного админом клиента по `/start <токен>`;
незнакомец купить доступ не мог. Требовалось дать покупку «с улицы».
**Решения Заказчика:**
1. **Момент создания клиента — первый шаг к оплате** (нажатие «Купить подписку» / «Пополнить»),
   а не `/start`. Открытие бота не оставляет следа в списке клиентов; записи заводят только те,
   кто реально пошёл платить.
2. **Набор доступов — все включённые инбаунды** на всех серверах (а не копия клиента-шаблона).
   Следствие, принятое осознанно: новый инбаунд не попадает автоматически к уже
   зарегистрированным — выдача фиксируется в момент создания клиента.
3. **Допуск — открытый:** любой, кто нашёл бота. Инвайт-кода нет.
**Защитные рамки (не обсуждались, введены по умолчанию безопасности):**
- Отдельный тумблер `billing_selfsignup_enabled`, **по умолчанию выключен** — иначе включение
  биллинга молча открывало бы продажу посторонним, что нарушает «панель для личного пользования».
- Новый клиент создаётся **выключенным и без подписки**: до оплаты он не попадает ни в один
  конфиг движка (sync берёт только `enabled = 1`), то есть доступа нет.
- Один клиент на один Telegram-чат: повторный заход находит существующего, дубли не плодятся.
**Остаётся риском:** при открытом допуске количество аккаунтов ограничено только числом
Telegram-аккаунтов у желающего. Если станет проблемой — вводить инвайт-код (см. отклонённый вариант).
